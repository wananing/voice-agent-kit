## 1. 目的、范围与术语

### 1.1 目的

1. 让"上游会话丢了、满了、要换了"成为**常规路径**，不再是故障路径（架构 §1 原则 3；BP B.1-2）。
2. 让模型在任何时刻看到的上下文都等于"用户实际经历过的对话 + 我们给的状态"，不多也不少（架构 §1 原则 2；KM 3.4）。
3. 让事实不经过 prompt 和历史记忆去"碰运气"（架构 §1 末尾"两条我们总结里有的原则"（事实走通道）；KM 3.7）。

### 1.2 范围

**在内**：本地对话记录、状态块、人设结构、事实通道的输入格式、历史进上游的规则、会话重建器、长会话与摘要、状态注入通道、上游错误分级、断线重连与多连接。

**不在内**（由其他规范负责，这里只引用接口）：回合状态机与判停（01）、输出仲裁与播放回执（02、01 §3.1.6）、工具注册表与收口终态（`closed_by`，03）、上游能力声明与原语（04）、出声前护栏、trace 权威字段表与评测 harness（06）。

**链路**：主要约束对象是 S2S 上游（A 类主链路、B 类低风险回合）。级联 / 半级联路径的"上游会话"就是我们每轮自己拼的消息，注入即生效（UM Q6），第 3、4、6 节中只和 S2S 会话语义有关的条款对它不适用，第 2、5、7、8 节仍然适用。每条规则是否适用于级联，在条款里单独说明。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| **本地上下文** | 我们在网关 / 编排层维护的对话记录 + 状态块 + 人设 + 工具表。**唯一真相**，所有重建、摘要、快照、评测都从它出发（架构 §1 原则 3；PC-B §1.1）。 |
| **上游会话** | S2S 服务端持有的一次会话（一条连接或一个 session id 对应的服务端状态）。生命周期由上游和我们共同决定，随时可能失效。 |
| **镜像** | 上游会话里的对话内容。它是本地上下文在某一时刻的投影，**只写不读**：不得从镜像反推本地记录，不得用镜像重放历史（LK-B §6.2：镜像不跟随截断，重放会把被打断的回复当成说完了）。 |
| **重灌** | 用本地上下文建一个新上游会话，并在**建会话参数**里带入历史。区别于"建会话后逐条插入"（后者【实测】0/6，总结 §5.4）。 |
| **状态块** | 放在系统提示末尾的、结构固定、带版本号的一段文本，描述"我们自己的数据当前是什么状态"（总结 §4.4）。 |
| **成对问答** | 历史灌入格式之一：user / assistant 交替的文本条目，每对对应一个回合（总结 §5.4【实测】6/6）。 |
| **已播放文本** | 某条 assistant 输出中用户实际听到的部分（A 类）或实际看到的部分（B 类上屏内容）。由仲裁器按播放回执 `played_ms` 截取（架构 §2.2；LK-B §6.1；UM Q3）。 |
| **会话重建** | 关闭（或放弃）当前上游会话，用 `(人设 + 状态块, 历史, 工具表)` 建一个新会话并交接。由唯一的**会话重建器**执行（BP B.2）。 |
| **主动换会话** | 不是因为出错，而是我们按自己的节奏（轮数、时长、状态变化）发起的会话重建（PC-B §2.3 Nova；LK-B §5 AWS）。 |
| **摘要** | 用我们自己的文本 LLM 把较早的已播放历史压成一段文本，在重建时代替那部分原始历史（LK-B §5 `_summarize`；PC-B §5）。 |
| **会话代数** | 同一个用户会话（本地）下第几个上游会话，trace 字段 `session_seq`（06 §3.6）。 |
| **用户会话** | 从用户开始对话到明确结束（或会话恢复窗口过期，§8.1）为止的本地会话，可以跨多个上游会话、多条连接，也可以跨多个 01 的连接会话（`session_id`，01 §1.3）。字段名 `user_session_id`（§2.1；06 §3.2）。 |

## 2. 数据模型

### 2.1 本地对话记录

**原则**：每一条"用户说过、系统出过声或上过屏、调用过工具"的事件都进本地记录；是否进上游历史、怎么进，由第 3 节的投影规则决定，不在记录时决定。

**条目 schema**（字段名为契约，存储格式各自实现）：

| 字段 | 类型 | 必填 | 说明 / 出处 |
|---|---|---|---|
| `entry_id` | string | 是 | 本地唯一 id。上行给上游的每个事件都带它或可映射到它，条目级错误才能定位（BP B.5；LK-B §2.2）。 |
| `user_session_id` | string | 是 | 用户会话 id（本地），与 06 §3.2 `user_session_id` 同值。不同于 01 的连接会话 `session_id`：续接窗口过期后连接会话换新，用户会话不变（review B-7-4）。 |
| `session_seq` | int | 是 | 产生该条目时的上游会话代数（06 §3.6）。 |
| `turn_id` | string | 是 | 所属回合（01 §2）。 |
| `sentence_id` | int | assistant 必填 | 下行分句 id，回合内从 0 递增，与播放回执对齐（01 §3.2.1、§3.1.6；架构 §2.2）。一句一条，或一条内含句列表，二选一，全仓统一。 |
| `role` | enum | 是 | `user` / `assistant` / `tool_call` / `tool_output` / `system_event`（断线、换会话、阶段切换等本地事件，不进上游）。 |
| `source` | enum | 是 | `model`（上游模型生成）/ `local`（我们合成的"自己的话"：本地直念的工具结果、事件播报、兜底话，总结 §5.5）/ `cue`（本地预合成提示语，架构 §2.2）/ `user_voice` / `user_ui`（B 类点选、改字段）。 |
| `presented_via` | enum | assistant 必填 | `voice` / `screen` / `both`（B 类上屏卡片、选项；A 类恒为 `voice`）。 |
| `text_generated` | string | 否 | 模型或模板生成的全文。**仅供 trace 和评测**，不得进上游历史、不得作为摘要输入。 |
| `text_presented` | string | assistant 必填 | 已播放（已上屏）文本。播完 = 全文；被打断 = 按 `played_ms` 截取；没播出 = 空（UM Q3；LK-B §6.1）。 |
| `text_user` | string | user 必填 | 定稿识别文本；`user_ui` 时为结构化动作的文字化描述（如"点选了第二个选项：X"）。 |
| `playback_state` | enum | assistant 必填 | `pending` / `playing` / `completed` / `interrupted` / `skipped`（一帧都没播出，LK-B §6.1）。以设备 / 客户端回执为准，不以服务端生成完为准（QW §2.3）。 |
| `interrupted` | bool | assistant 必填 | 是否被打断。 |
| `interrupt_at` | object | 被打断时必填 | `{played_ms, char_offset, estimated: bool}`。`played_ms` 来自回执；`char_offset` 是换算到文本的位置。模型的话 S2S 下有精确 `audio_end_ms` 但文本是估算；本地合成的话按 TTS 对齐或按字匀速估算，`estimated` 标出来（LK-B §6.1：中文按单字匀速，误差未确认）。 |
| `t_start` / `t_end` | timestamp | 是 | 用户：说话起止（或按键起止）；assistant：`playback.started` / `ended|interrupted` 时刻。统一时钟口径见 06 §2.1。 |
| `tool_call_id` | string | tool_* 必填 | 关联的工具调用 id；`tool_call` 条目记工具名、参数；`tool_output` 条目记结果摘要与 `closed_by`（六个终态之一，03 §4.2）。 |
| `related_entry_ids` | string[] | 否 | assistant 条目关联到它所呈现的 `tool_output`（如本地直念某个工具结果）。 |
| `upstream_synced` | enum | 是 | `none` / `live`（在当前上游会话中已存在，如上游自己生成的回复或已回传的工具结果）/ `seeded`（由重灌带入）。用于重建"已回传"登记表（§4.6）。 |
| `write_effect` | object | tool_call 且为写操作时必填 | `{idempotency_key, executed: bool, result_ref}`。断线重放的前提（§4.5）。 |

**记录规则**：

1. assistant 条目在**播放回执到达后**才确定 `text_presented`；回执缺失时按"未播出"处理，不得按全文补记（UM Q3 的做法是按播放时刻释放词；QW §2.3 以 `playback.started` 为送达依据）。
2. `source=cue` 的条目**只进本地记录，永不进上游历史**（架构 §1 原则 9：提示语走旁路不进模型）。
3. `source=local` 的条目（"自己的话"）必须整句记录；被打断时和模型的话一样截取（LK-B §7.1-③）。
4. 同一回合被上游切成多段的用户语音，本地合并为一条 `user` 条目，段数记入 trace `server_vad_segments_in_turn`（06 §3.7；BP B.3）。被 01 §2.6 `turn.merge` 合并的两次按键同样只记一条 `user` 条目，`turn_id` 取合并后的值（`into`）。
5. 用户会话内条目只追加不改写；摘要不改原始条目，摘要本身作为独立对象保存（§5.3）。

### 2.2 状态块

**定位**：模型负责选动作，就必须看得到选择所需的状态（总结 §4.4）。状态块是"我们自己的数据"的当前值，不是事实库，也不是对话记忆。

**结构规则**：

| 规则 | 要求 | 出处 |
|---|---|---|
| 结构固定 | 字段集合和顺序由 schema 定义，按 profile 各一份；不得在运行时增删字段，空值写"无"而不是省略。 | 总结 §4.4 |
| 版本号 | 两个版本：`schema_version`（结构变了才升）和 `state_rev`（每次内容变化 +1）。两者都写进每轮 trace 的 `prompt_version`（06 §3.2）。 | 总结 §4.4；KM 2.12 |
| 只放我们的数据 | 允许：任务 / 流程进度、用户选择、用户告知的硬信息（称呼、陪同人等）、当前阶段、"刚说到的点"。**不得**放业务事实（地点介绍、价格、规则、知识库内容）——那些走事实通道（§2.4）。 | 总结 §4.4、§3.2 |
| 长度上限 | 【建议值，需实测】≤ 260 字（中文字符）。这是 A 类现有实践值（总结 §4.4）；B 类表单字段多，上限另定，超出部分只保留"与当前阶段相关的字段"，其余留在屏幕和后端。 | 总结 §4.4 |
| 位置 | S2S：系统提示末尾（总结 §4.4）。自控级联 / 文本 LLM：**消息尾部**，保证前缀稳定、前缀缓存可命中（KM 3.4；UM Q6：unmute 把指令放 `chat_history[0]`，不要照搬）。 | |
| 语言 | 用自然短句，对模型可读；不写 JSON（避免模型模仿格式说话，同 PC-B §7.1 M5 的风险）。【建议，需实测】 | |

**两层生效语义**（BP B.4；LK-B §7.1-⑤）：

| 层 | 含义 | 典型字段 | 生效方式 |
|---|---|---|---|
| **立即生效** | 不及时更新会导致下一轮选错动作 | 选定的任务 / 路线、新建任务、特殊模式（如带孩子）、B 类阶段切换 | 两轮之间走会话配置更新或会话重建（§6） |
| **懒生效** | 晚几轮不影响动作选择 | 进度计数、次要偏好、"刚说到的点" | 只更新本地，下一次重建或下一次立即生效更新时顺带带上 |

- 每个字段在 schema 里声明所属层，不得运行时判断。
- 反例警示：总结 §5.4 中"开始吧"组从 8/16 升到 15/16 靠的是状态及时更新【实测】，所以不能为了省预填把所有字段都放懒生效层。
- "刚说到的点"只在重建时写入状态块，会话中靠对话本身（总结 §4.4）。

**更新时机**：只在两轮之间更新；回合进行中的变化排队。检查点：回合结束、下一次回合开始前（A 类：下一次按键前）、文本回合前（总结 §4.4）。更新前等上游空闲（QW §2.6 `whenIdle`）。

### 2.3 人设结构

人设是**分节清单**，不是散文（总结 §4.6）。

| 节 | 内容 | 可检查性 |
|---|---|---|
| 角色 | 是谁、怎么自称、用户怎么称呼 | — |
| 背景 | 来历（第一人称） | 不得含可被当作事实引用的数字、日期、地名 |
| 性格 | 3–5 个形容词 | — |
| 语域 | 对不同用户群的说法差异（如对孩子 / 对大人的句长与称呼） | 句长可测 |
| 硬规则 | 每轮一两句、数字口语化、先结论后理由、一次只问一个问题（A 类最多两个选项）、禁 markdown / 列表 / emoji | **必须能写成自动检查**（KM 2.7 语音 prompt 约定） |
| 禁用词 | 去客服味的禁用词表 | 进测试，对照人设、话术模板、提示语三处（总结 §4.6） |
| 边界 | 事实只能说被告知的；超出范围的统一说法 | 与事实通道配合 |

规则：

1. **人设里不写事实。** 包括业务事实、工具说明、路由规则（KM 2.7、3.7；QW 把"人设里涉及工具、路由、事实的内容一律无效"写成对模型可见的规则，可借鉴）。
2. 人设与规则可以分文件（KM 2.7 qwen 的 `ASSISTANT.md` / `PROMPT.md` 拆分），但拼进系统提示时顺序固定：人设 → 规则 → 状态块（状态块在最后）。
3. 人设有版本号，进 trace（总结 §4.6）。人设变更只在新建会话时生效，**不在会话中途更新**（避免预填代价，§6）。

### 2.4 事实通道的输入格式

事实不走人设、不走历史记忆，走三条通道（架构 §1 末尾"两条我们总结里有的原则"（事实走通道）；总结 §3.2；KM 3.7）。通道是工具注册表的"呈现方式"属性，这里只规定**进入上下文时的格式**。

| 通道 | 何时用 | 输入格式 | 进本地记录的方式 |
|---|---|---|---|
| **逐字念** | 关键事实：位置、时间、数字、状态结果 | 我们写好的最终文本（已口语化、数字已转读法），附 `fact_ref`（数据来源 id + 版本）。契约内只有本地 TTS 直念一条通道；上游"直接念文本"为**实验，待 P0-13 通过后按 04 Q12 以 `request_response.overrides.verbatim_text` 承载，不设独立原语**（review B-6）。首音 0.6–0.7 s【实测，总结 §3.2；起点待核实，06 §10.2 问题 2】 | `assistant, source=local` + `related_entry_ids` 指向 tool_output |
| **上屏**（B 类） | 清单、多选项、需要确认的字段 | 结构化数据（字段名、值、单位、可选项、`fact_ref`），语音只念要点 | `assistant, presented_via=screen|both`；`text_presented` 记上屏内容的文字化摘要 |
| **RAG 注入** | 讲解类 | 分层资料卡：简介 / 正文 / 细节三层，每次只给当前层；附约束说明（"只用资料内的信息"）和 `fact_ref`。分层对象是**刚讲过的点**而不是当前任务位置（总结 §3.2） | 注入内容本身作为工具结果（`tool_output`）记录；模型据此生成的回复按普通 `model` 条目记 |
| 替代方案 | 做不到时 | 随结果下发的结构化备选（如 `alternative_times`），不让模型自己编（KM 3.7） | 同所属通道 |

注意：RAG 通道下模型仍会在资料外补细节（总结 §3.2），所以关键数字不得只走 RAG。

## 3. 历史进上游的规则

### 3.1 只在建会话时带入

1. **历史必须通过建会话参数带入**（重灌）。【实测】建会话时带入成对问答 6/6；会话 id 接续 1/6；建会话后逐条插入 0/6；中途插入 system / user 条目说明状态"基本不看"（总结 §5.4）。开源印证：Pipecat 所有 S2S 服务中途只同步工具结果（PC-B §1.1）；LiveKit 不可变上游（AWS、GPT-Live）只在建会话时带入（LK-B §2.3）。
2. **不得**照搬"建会话后逐条插入并丢弃工具调用"的重连方式（LK-B §2.1 OpenAI 插件，正是 0/6 的做法）。
3. 上游对历史的结构要求由适配层能力声明给出（§3.7），常见的有：历史须以 user 开头（不满足时补一条语义占位，如"（继续刚才的对话）"，LK-B §7.1-② 参考 AWS `[Resuming conversation]`）、历史须以 user 结尾（Gemini 2.5，PC-B §1.2）、历史须在音频开始前发完（AWS，LK-B §2.3）、条数 / 字节上限（AWS 40 条、GPT-Live 128 条 / 8192 token、Nova 单条 50 KB / 总量 200 KB，LK-B §5、PC-B §2.3）。
4. 级联路径不受本节约束：每轮自己拼消息（UM Q6）。

### 3.2 三种灌入格式

格式由 B-X2 实验（BP B.8）选定，选定前默认成对问答（现状）。每个上游只允许用一种，写进能力声明。

| 格式 | 做法 | 已知风险 | 出处 |
|---|---|---|---|
| **成对问答**（默认） | user / assistant 交替文本条目 | 只测了 6 次、只测了"名字"一类问题；文本条目可能影响音频会话的回复模态（§3.5） | 总结 §5.4【实测】6/6 |
| **打包成一条** | 整段历史放进一条消息，前后加说明文字 | 模型可能把它当成要回答的问题；需要结尾说明（如"这是之前的对话，只用于衔接，不是新请求"）。qwen 的 `<restored_context>` 是同类，但它在建会话后插入，效果无评测数据 | PC-B §1.2、§7.1 M4；QW §2.6 |
| **工具调用转文字** | 成对问答 + 工具调用和结果转成文字描述 | 模型可能模仿 `[Called function …]` 的格式说话 | PC-B §1.2（Gemini 灌带 tool call 的历史会报 1007） |

B-X2 的通过标准：各类回忆（名字、陪同人、"刚才第二个"、刚调过的工具结果）正确率不低于现状；纯文本回复轮数为 0；首轮不把历史当问题回答、不模仿格式（BP B.8）。

### 3.3 assistant 文本：用户实际听到（看到）的

1. 投影到上游历史的 assistant 文本**一律取 `text_presented`**，不得取 `text_generated`（KM 3.4；LK-B §7.1-③；UM Q3）。
2. `playback_state=skipped` 的条目不进历史。
3. 被打断的条目必须带**显式打断标记**，让模型知道"自己被打断了"。不得像 unmute 那样去掉标记只留半句（UM Q3：它为防止模型学着输出破折号而删掉 `—`）。标记用自然语言而不是符号，例如在文本后接"（说到这里被用户打断）"。【建议写法，需在 B-X2 中一并验证模型是否模仿】
4. "自己的话"（`source=local`）和模型的话同等进历史，这样模型知道"自己说过"（总结 §5.5；缓解受限 6 的上下文一侧，BP B.2）。
5. B 类上屏内容：用文字化摘要作为 assistant 一侧（如"（屏幕上展示了 3 个选项：……）"），不把完整卡片数据灌进去。【建议，需实测】

### 3.4 工具调用在历史里怎么保留

1. **本地记录永远保留完整的 `tool_call` / `tool_output`**（§2.1），这是审计、重放判定和摘要的依据。
2. 进上游历史时，按能力声明选一种，**不得静默丢弃**（Nova、OpenAI 插件丢弃工具调用是已知问题，LK-B §2.1、PC-B §1.2）：
   - 上游支持在初始化历史里带原生工具条目且不报错：带原生条目。【未验证，需 P0 探针确认】
   - 否则：按 §3.2 "工具调用转文字"格式；或把结果并入它所呈现的那条 assistant 文本（因为逐字念 / 本地直念的结果本来就是用户听到的话）。
3. 影响后续动作的工具结果（如"已创建任务 X"）**同时写进状态块**，不依赖历史里的工具条目（总结 §5.4：早期信息要单独收进状态块）。
4. 未收口的调用（没有 `closed_by`）不得进历史；摘要也不得切断未完成的调用（PC-B §5 `LLMContextSummarizer`）。

### 3.5 文本条目污染音频会话与 `reply_modality` 监控

**风险**：往音频模态会话里灌文本条目（成对问答、补记的"自己的话"、摘要），模型可能改用纯文本回复、不出音频。LiveKit 有专门报错（LK-B §4.2）；Pipecat 注释写明 OpenAI 逐条插入后"模型会忘了自己能出音频"（PC-B §1.2）。我们的 6/6 实测没有检查之后的回复模态（LK-B §7.2）。

**要求**：

1. 每轮 trace 必须记 `reply_modality`（`audio` / `text_only` / `mixed` / `none`，06 §3.6）。
2. 线上告警：音频会话中出现 `text_only` 即告警（目标为 0）。
3. 运行时兜底：出现 `text_only` 时，把这段文本交本地 TTS 出声，本回合不静默（LK-B §4.1 框架在音频会话收到文本时退回 TTS 的做法）；同时计一次"模态异常"，同一上游会话内【建议值，需实测】累计 2 次则在下一个空档主动换会话。
4. E-B4（LK-B §7.3）若显示补记或灌入导致纯文本回复轮数 > 0，改为"只进系统提示"的写法（把必要的前情并入状态块），不再以对话条目形式带入。

### 3.6 中途插入：默认不允许

会话进行中向上游插入内容**不可靠**（§3.1 数据）。只在以下四种情况允许：

| 允许的情况 | 条件 | 出处 |
|---|---|---|
| **工具结果回传** | 对应上游本会话发起的调用（`tool_call_id` 在"已回传"登记表的在途集合里）；回传是为了收口，是否让模型再说由工具属性决定 | PC-B §1.1（所有 S2S 服务中途唯一同步的内容）；架构 §1 原则 1 |
| **按回复覆盖** | 上游支持按单次回复带指令（如 OpenAI `response.create{instructions}`）；只用于状态块，不用于历史；**不支持时不得退化为写一条对话项**（那样会进入历史，QW §2.6 `perResponseInstructions`） | LK-B §1.6；PC-B §1.3；是否破坏缓存【未确认】 |
| **追加通道** | 上游协议有专门的"追加、不重写前缀"事件（如 OpenAI Live `session.instructions.append` / `thinking.append` / `commentary.append`，每条 ≤ 500 token） | PC-B §1.3 |
| **已回传调用的打断标记** | 该调用已按 03 §7.1 立即回传（`delivery: in_progress`），正文播放中被打断；补一条 `{"interrupted": true}`（是否附 `played_text` 由 A-E1 定）；通道（新建条目 / 同一 `call_id` 再回传）按 04 P0-16 的结论 | 总结 §5.3【实测】补 20/20、不补 15/20；03 §5.1 行 4；review B-2 |

**明确禁止**：中途插入 system / user 条目描述状态；逐条插入历史；用会话 id 接续代替重灌（总结 §5.4）。

**"自己的话"补记进上游：分通道（已决定，review B-3）**。总结 §5.5 的现状是"自己的话"播完后以成对问答补记进上游，它属于中途插入，且有 §3.5 的污染风险。决定按内容分通道，只走已被证明可靠的通道：

1. **与工具调用相关的**（本地直念的工具结果、A2 委派播出的正文）：经该调用的 function output `spoken_to_user` 带给上游（03 §7.1），属于上表第一种"工具结果回传"。
2. **与调用无关的 narration**（到点提醒、后台结果播报、兜底话）：只写本地记录（`source=local`），下一次重建时进历史（§3.3 第 4 条）。
3. **其中要紧的事实**（会影响后续追问或动作的）：写进状态块的懒生效层（§2.2），随下一次重建或立即生效更新带上。

**上线前先跑 B-X2**（BP B.8；同时看 E-B4 关心的 `reply_modality` 和回忆率），**跑完前线上保持现行做法**（中途成对问答补记）。

### 3.7 能力声明（适配层需提供）

与本规范相关的能力字段（BP B.7；LK-B §1.1；PC-B §6；QW §2.6）：历史注入方式、历史结构约束（开头 / 结尾角色、条数、字节）、工具条目能否进初始化历史、会话配置能否中途更新及是否重新预填、是否支持按回复覆盖指令 / 模态、是否有追加通道、能否按播放位置截断、会话时长上限、空闲超时、会话续接能力（resumption handle）、是否上报缓存命中、上下文超限的错误码。**策略不得写进适配层**（PC-B §6：Pipecat 把策略写在各服务里导致不一致）。

## 4. 会话重建器

### 4.1 接口与唯一性

- **输入**：`(人设 + 状态块, 历史, 工具表)`，其中历史是按 §3 从本地记录投影出来的结果（可能含摘要，§5）。
- **输出**：一个已就绪的新上游会话 + 新的 `session_seq` + 新的"已回传"登记表。
- **唯一性**：全系统只有一个重建器实现，所有触发都走它（BP B.2；LK-B §7.1-②）。不允许断线重连、主动换会话、错误恢复各写一份。
- 每次重建写 trace（字段定义见 06 §3.6）：`session_seq`、`rebuild_reason`、`history_format`（灌入格式，§3.2）与 `history_scope`（全量 / 截断 / 摘要 + 最近 K 轮）、`history_items`、`handoff_start_at_ms / handoff_done_at_ms`、首轮 `cached_input_tokens` / `uncached_input_tokens`。

### 4.2 触发条件

| `rebuild_reason` | 条件 | 交接方式 | 出处 |
|---|---|---|---|
| `disconnect` | 连接断开、服务端关闭会话 | 立即重建（不等空档，旧会话已不可用），受重建预算约束（§7.2） | BP B.5 |
| `upstream_error` | "会话失效可重建"类错误（§7.1，`error_class=transient`） | 同上 | BP B.5 |
| `state_change` | 立即生效层的状态变化，且选定的注入通道是"重建"（§6） | 等空档 | BP B.4 |
| `turn_limit` | 上游保留轮数接近上限。上游约保留 20 轮【实测，总结 §5.4】；触发阈值 N 【建议值，需实测】取 {8, 12, 16} 之一，由 B-X4 定 | 等空档 | BP B.8 B-X4 |
| `scheduled` | 上游会话时长接近上限或定时回收周期。参考：LiveKit OpenAI 20 min、AWS 6 min、Nova 360 s（硬上限约 8 min）【开源】 | 等空档 | LK-B §2.1、§5；PC-B §2.3 |
| `context_overflow` | 上下文超限错误（如 Gemini 1007，`error_class=context_overflow`） | **先缩历史**（摘要或截断）再重建，否则原样失败 | LK-B §2.2；BP B.5 |
| `modality` | §3.5 模态异常累计达阈值 | 等空档 | 本规范 |

### 4.3 交接时机（空档判定）

非紧急触发（`state_change` / `turn_limit` / `scheduled` / `modality`）必须等空档，空档同时满足：

1. 助手已说完：当前回合的所有 assistant 条目 `playback_state ∈ {completed, interrupted, skipped}`；
2. 没有未收口的工具调用；
3. 连续约 1 s 没有新的下行音频（AWS 做法，LK-B §5）【开源，1 s 为建议值，需实测】；
4. 用户不在说话：A 类按键模式为"松键之后、下一次按键之前"（BP B.2；按键天然有这个空档，PC-B §2.3）；开放麦模式为 VAD 无人声且判停不在进行中。
5. 状态块没有排队中的更新（有则在本次重建一并带上）。

**等待上限**：空档迟迟不出现时，`scheduled` / `turn_limit` 类在【建议值，需实测】超过阈值后 60 s 仍未等到空档，降级为"下一回合结束时强制交接"；不得在助手说话中途切断（Nova 等 80 s 后强制切换，PC-B §2.3，仅作参考）。

### 4.4 预建 vs 串行回收

| 方式 | 做法 | 优点 | 代价 | 出处 |
|---|---|---|---|---|
| **预建** | 后台提前建下一个会话，预灌系统提示；历史和缓冲音频留到交接时发 | 交接快 | 上游空闲超时（Nova 30 s 就得重建预建会话）；预建会话是否计费未知；预灌的状态块可能在交接前过期 | PC-B §2.3 |
| **串行回收** | 等空档 → 结束旧会话（AWS 等 `completionEnd` 最多 2 s）→ 建新会话 | 简单、状态最新 | 交接期用户若开口要缓冲 | LK-B §5 |

- 两种实现来自同一家模型（Nova），不算独立印证（BP B.1-2）。
- 选型由 B-X4 决定；决定前默认**串行回收**（实现简单，A 类按键空档足够）。【建议，需实测】
- 紧急触发（`disconnect` / `upstream_error` / `context_overflow`）没有旧会话可等，二者等价于"立即新建"。
- 预建时：交接前状态块若有变化，必须按新版本重建或在交接时通过 §6 通道补齐，不得带着过期状态块交接。

### 4.5 被断线打断的回合：最后一句 user 的重放

当重建发生时最后一个回合没有终态（例如用户说完、上游还没回复或回复中断线）：

1. 从投影历史里拿出最后一条 `user` 条目，不作为历史，而作为新会话的**首轮输入**触发回复（LK-B §2.3 AWS 做法；或 LiveKit fallback 的 `regenerate_on_swap`，LK-B §2.4）。
2. **前提：写操作不会重复执行。** 判定：
   - 该回合没有发起写操作 → 可以重放；
   - 该回合已发起写操作且 `write_effect.executed=true` → **不重放**，改为按结果收口：用本地通道把结果告诉用户（逐字念 / 上屏），并把结果写进状态块和本地记录；
   - 写操作状态未知 → 不重放，先用幂等键查后端状态，再按上一条处理；查不到时说一句兜底话请用户确认。
   - 所有写工具调用必须带 `idempotency_key`（与 `turn_id` + 工具名 + 参数绑定），后端按键去重，作为最后一道保险。【建议，需实测，B-X3 / E-B5】
3. 用户正在说话时断线：已缓冲的用户音频按 §4.7 回放给新会话，不做文本重放。
4. 被打断的 assistant 回复（已播放一部分）按 §3.3 带打断标记进历史，**不自动重说**（架构 §1 原则 6：被打断的播报不重播）。
5. 对照组"丢弃该回合 + 兜底话"保留为降级方案；两者对比见 E-B5（LK-B §7.3）。

### 4.6 重建"已回传"登记表

1. 新会话建立时，登记表重新初始化：历史里带入的工具结果标记为 `seeded`，**不得**作为"新完成的结果"再次回传（PC-B §2.2：Gemini 重连后清空登记表而未重建，推断会重发全部历史工具结果）。
2. 旧会话上的在途调用：新会话不认识它的 `tool_call_id`，**由本地收口**（BP B.2；PC-B §2.2 示例注释）。已完成的结果走本地通道呈现（逐字念 / 上屏 / narration）并写本地记录；未完成的继续在我们这边执行，结束后同样走本地通道。`closed_by` 按 03 §4.1 不变式 4 取值（重建前在途的调用收口为 `superseded`）。
3. 新会话若回放或重发旧调用（`tool_call_id` 已终结），按 `duplicate` 收口，不执行（03 §4.2）。

### 4.7 交接期音频缓冲与回放

1. 交接开始到新会话就绪之间，用户音频一律本地缓冲，不丢弃（BP B.2；PC-B §2.3 Nova 回放约 3 s 缓冲音频）。
2. 缓冲上限【建议值，需实测】10 s；超出时停止上行缓冲并给用户一句本地提示语（cue）。
3. 回放顺序：建会话参数（人设 + 状态块 + 历史）→ 首轮输入（§4.5 重放的 user，若有）→ 缓冲音频。缓冲音频在需要"以 user 结尾"的上游上，排在历史之后。
4. 回放可以快于实时（推送不需要按实时速率，LK-B §7.1-①），但要遵守上游输入限速。
5. 交接期间的出声只允许本地 cue 和本地 narration，受仲裁器约束；`speech` 类输出等新会话就绪。
6. 验收：交接期音频丢失为 0（BP B.8 B-X4）。

## 5. 长会话

### 5.1 摘要触发

1. **提前做，不等换会话。** 摘要在后台异步生成，完成后缓存，等下一次重建时使用（BP B.2；LK-B §7.1-④）。
2. 触发点【建议值，需实测】：距上次摘要新增的回合数达到 `turn_limit` 阈值减 6（例如阈值 20 轮时第 14 轮开始，BP B.2 的示例值），或投影历史的估算长度达到上游历史上限的 70%。Pipecat 默认 8000 token 或 20 条消息触发（PC-B §5），仅作参考。
3. 摘要结果回来时，如果被摘要范围内的本地记录已变化（例如最后几轮被打断改写了 `text_presented`），放弃这次结果重做（PC-B §5）。打断不取消摘要任务（PC-B §5）。
4. 摘要生成用我们自己的文本 LLM；S2S 上游不承担摘要（PC-B §5：S2S 服务都没实现 `run_inference`；LK-B §5：`_summarize` 要求文本模型）。

### 5.2 摘要输入

- 只用 `text_presented`、`text_user` 和已收口的 `tool_output`；不得使用 `text_generated`（BP B.2；LK-B §7.2：否则会把没播出去的内容当成已说）。
- 工具结果提炼成"已知信息"（LK-B §5 `_summarize` 提示词）；保留关键事实、用户偏好、未决事项，省略寒暄（PC-B §5 默认提示词）。
- 不切断未完成的工具调用：遇到未收口的调用，摘要截止点前移（PC-B §5）。

### 5.3 摘要放置位置

两个候选，由 E-B2 / B-X4 决定（LK-B §7.1-④）：

| 位置 | 做法 | 风险 |
|---|---|---|
| 历史开头的一对问答 | user 侧为语义占位（如"（之前聊过的内容）"），assistant 侧为摘要；LiveKit 用 assistant 消息 `<chat_history_summary>` | 文本条目的模态风险（§3.5） |
| 并进系统提示 | 放在人设之后、状态块之前的"前情"一节 | 系统提示变长；每次摘要更新即前缀变化 |

决定前默认"历史开头的一对问答"。【建议，需实测】Pipecat 的做法是把摘要作为 user 消息（PC-B §5），不采用：user 侧的摘要可能被当作新请求。

### 5.4 硬信息走状态块

名字、陪同人、是否带孩子、已确认的选择等**硬信息必须在状态块里**，不依赖摘要或历史（KM 3.4；总结 §5.4；PC-B §7.1 M2）。摘要里出现的硬信息与状态块冲突时，以状态块为准。

### 5.5 最近 N 轮原样保留

重建时历史 = `[摘要] + 最近 K 轮原样（成对问答或选定格式）`。K【建议值，需实测】取 4–6；LiveKit 默认保留最后 2 轮（LK-B §5），总结 §4.5 的快照保留最近 12 轮。E-B2 比较"全量 / 最近 N 对 + 状态块 / 摘要 + 最近 N 对 + 状态块"三种（LK-B §7.3）。

### 5.6 不对摘要再摘要

新摘要的输入 = 上一版摘要覆盖范围之后的原始条目 + 上一版摘要**覆盖范围内的原始条目**（重新从本地记录生成），而不是"上一版摘要文本 + 新条目"。摘要对象带 `covers: [first_entry_id, last_entry_id]` 和 `is_summary=true`（LK-B §5 `extra.is_summary`）。当覆盖范围过长导致摘要输入超出文本 LLM 预算时，按时间分段摘要后拼接，仍不对摘要文本再压缩。【建议，需实测】

### 5.7 B 类：一任务一会话 + 结构化产出物

B 类以"任务"而非"时长"组织上下文（架构 §3.2、§3.4）：

1. **一任务一用户会话。** 任务开始建会话，任务结束关闭；同一任务内的上游会话更替仍走重建器。
2. **上下文主体是结构化状态（表单）+ 摘要**，原始对话只保留最近几轮（架构 §3.2）。表单是状态块在 B 类的形态：字段可见、可改、有版本；用户在屏幕上改字段等于一次输入（`user_ui` 条目），触发状态块更新（按字段所属层生效）。
3. **阶段切换是立即生效层的状态变化。** 阶段决定模型可见的动作集，但动作集的收窄在工具层实现（拒绝并收口），**不改工具表**（§6.3；KM 2.7；BP B.4）。
4. **结束时生成结构化产出物**：输入为最终表单 + 摘要 + 已播放 / 已上屏文本；产出物带 schema 版本、生成时刻和来源条目范围；展示给用户确认后写回业务后端（架构 §3.2、§3.4 原则 5）。后端是唯一真相，产出物写回失败要可重试且幂等。
5. B 类以级联为主时，表单直接进每轮消息尾部即时生效（UM Q6）；路由到 S2S 的回合才受第 3、6 节约束。混合路由下 S2S 会话对级联回合的感知问题见 §10.2。

## 6. 状态注入通道选择

### 6.1 通道对比

| 通道 | 生效时机 | 代价 | 前提 | 出处 |
|---|---|---|---|---|
| **会话配置更新** | 下一轮 | 上游重新预填整段对话，未命中缓存的输入 ×3.2；首音粗粒度更新 +80–200 ms，每轮都更新 +150–270 ms【实测】 | 上游允许中途更新配置 | 总结 §5.4；KM 3.4 |
| **按回复覆盖** | 本次回复 | 不改会话配置；是否同样使缓存失效【未确认】 | 上游支持按回复带指令 | LK-B §1.6；PC-B §1.3 M11 |
| **追加通道** | 追加后 | 不重写前缀；单条长度受限（OpenAI Live ≤ 500 token）；效果【未确认】 | 上游协议有追加事件 | PC-B §1.3 |
| **会话重建** | 新会话 | 缓存全冷；交接逻辑（§4） | 任何上游 | BP B.2 |
| **懒生效** | 下一次重建或下一次立即更新 | 状态滞后若干轮 | 任何上游；字段属于懒生效层 | BP B.4；LK-B §1.6 AWS；PC-B §7.1 M3 |

### 6.2 选择规则

按上游能力（§3.7）从上到下选第一个可用的：

1. **懒生效层字段**：一律懒生效，不单独触发任何上游操作。
2. **立即生效层字段**：
   1. 上游支持按回复覆盖且 B-X5 / E-B3 确认不破坏缓存 → 按回复覆盖（每次回复都带当前完整状态块）；
   2. 上游有追加通道且 B-X5 确认有效 → 追加（只追加变化的字段，并在下次重建时合并回系统提示）；
   3. 上游允许中途更新配置 → 在两轮之间、上游空闲时做配置更新（B-X5 比较"回合开始前"与"空闲时"两个时点）；
   4. 以上都不可用（不可变上游）→ 在空档触发重建（`rebuild_reason=state_change`）。
3. 同一空档内有多个变化时合并为一次操作。
4. 每轮 trace 记录缓存命中 token，把重新预填变成可量化指标（BP B.4；PC-B §7.1 M9）。
5. 验收门槛：多轮上下文用例不低于 76/78，"开始吧"组不低于 15/16，首音增量 < 80 ms（BP B.8 B-X5）。

### 6.3 工具表固定

- 工具表在建会话时一次性给全，**会话中不改**（Gemini、Ultravox、AWS 改工具都要重连；Gemini 按回复限制工具会触发两次重连，LK-B §1.6、§7.1-⑥）。
- 按状态 / 阶段限制工具：在工具层拒绝（返回"当前不可用"，调用照常收口），不改会话配置（BP B.4）。
- 工具表版本进 `prompt_version`；工具表变更只随新用户会话或重建生效。
- 人设同理，只在建会话时生效（§2.3）。

## 7. 错误分级与重建预算

### 7.1 四类错误

在"致命 / 非致命"之上细分为四类（BP B.5；LK-B §2.2、§7.1-⑦；PC-B §2.2）。四类的取值是一套枚举：适配层事件的 `error.class`（04 §4.6）与 trace 的 `error_class`（06 §3.9）都用下表最后一列的值：

| 类别 | 例子 | 处理 | trace `error_class` |
|---|---|---|---|
| **重建也没用** | 鉴权失败、配额耗尽、计费上限、账号停用 | 停止重建；说一句本地兜底话（预合成，A 类必须能出声）；告警；本回合以错误终态结束 | `fatal` |
| **会话失效，可重建** | 断线、服务端关闭会话、流异常、上游限流 / 模型未就绪类可重试错误 | 走重建器（§4），受重建预算约束（§7.2）；补一句"信号不好"类本地话术（总结 §5.7） | `transient` |
| **上下文超限** | 类似 Gemini 1007 | 先缩历史（用已缓存的摘要；没有则截断到最近 K 轮 + 状态块）再重建；**不得原样重放** | `context_overflow` |
| **非致命** | 取消竞态、审核命中、条目级错误、空提交 | 记日志，只让这一回合或这一条失败，会话继续 | `benign` |

说明：

- "重建也没用"采用**白名单**：只有明确列出的错误码属于此类（LK-B §2.2：OpenAI 插件的四个致命码；注释说明重连能成功但每次生成都失败，会无限循环）。
- 错误码不在任何名单中时，默认按"会话失效，可重建"处理，受预算保护。
- 审核命中：我们按非致命处理（总结 §5.7）。qwen 的做法是隔离出错回合后重建会话（QW §2.6），代价是缓存全冷，不采用；但**被拒的回合内容不得进后续历史**（借鉴 qwen 的隔离思路），避免重建时再次触发。
- 条目级错误要能定位到具体条目，前提是每个上行事件带 id（BP B.5）。

### 7.2 重建预算

| 参数 | 值 | 出处 |
|---|---|---|
| 每回合最多重建次数 | 3 | AWS `DEFAULT_MAX_SESSION_RESTART_ATTEMPTS=3`（LK-B §2.2）；Gemini 连续 3 次（PC-B §2.2） |
| 退避 | 指数退避，封顶 10 s；首次重试【建议值，需实测】≤ 0.5 s（A 类沉默即故障） | LK-B §2.2 AWS；架构 §2.4 |
| 计数清零 | 连接稳定 10 s 后清零 | PC-B §2.2 Gemini |
| 用尽后 | 升级为"重建也没用"的处理：停止、兜底话、告警；用户下一次主动发起回合时允许重新开始计数 | PC-B §7.1 M7 |

- 预算按回合计，防止一个"毒回合"（某段输入反复触发上游错误）拖出无限重建（LK-B §7.1-⑦）。
- 主动换会话（`state_change` / `turn_limit` / `scheduled` / `modality`）不消耗错误预算，但若主动换会话本身失败，按其错误类别计入。
- 重建期间，A 类必须在 2 s 内有声音（本地 cue），B 类同时显示状态（架构 §2.4 原则 1、§3.2）。

### 7.3 非致命白名单

- 维护一份**按上游**的非致命错误码白名单，作为适配层能力声明的一部分；策略判断在链路无关层（BP B.7）。
- 起始条目（参考，按各上游实际错误码替换）：`response_cancel_not_active`、`conversation_already_has_active_response`（PC-B §2.2）、`Cancellation failed` 前缀消息、服务端 VAD 已提交时的 `input_audio_buffer_commit_empty`（LK-B §2.2）、工具结果解析类错误（AWS "Tool Response parsing error"，关掉当前生成、清掉 pending 工具，会话继续，LK-B §2.2）、`item_create_duplicate_item_id` 视为成功（LK-B §1.4）。
- 错误码不稳定的上游按消息子串兜底（PC-B §2.2 xAI）。
- 白名单漏项的代价是不必要的重建（PC-B §7.1 M8），所以每周回放错误日志按四类重标（B-X3 / E-B6）。

## 8. 断线重连与跨设备

### 8.1 会话恢复窗口

本节的窗口叫"会话恢复窗口"，与 01 §6.2 的"续接窗口"（默认 30 s）不是同一个：续接窗口内网关连上游会话都还在，客户端带 `session_id` 续接；续接窗口过期后（01 返回 `session_expired`、客户端重新 `hello`、拿到新的 `session_id`），只要仍在本节的恢复窗口内，就按快照恢复同一个用户会话。

- 设备 / 客户端断线后，在会话恢复窗口内重连视为**同一个用户会话**：状态和对话记录恢复，上游会话按 §4 重建（`rebuild_reason=disconnect`）。
- 窗口【建议值，需实测】：A 类 30 min（总结 §4.5 现有实践）；B 类以任务为界，任务未结束时默认 30 min，App 切后台期间窗口不计时的策略另定。
- 恢复窗口过期后，新连接开始新的用户会话；旧会话的硬信息是否带入由业务决定，不属于本规范。
- 用户主动"重新开始 / 换个话题"是开新会话的唯一主动方式，分两档：只清对话，或连业务状态一起清（总结 §4.5）。
- 不依赖上游的会话续接能力（session id / resumption handle）替代重灌：会话 id 接续【实测】1/6（总结 §5.4）；Gemini resumption handle 只存在内存、不跨进程（PC-B §2.3），可作为优化项单独评测。

### 8.2 快照内容与存储

| 内容 | 说明 | 出处 |
|---|---|---|
| 业务状态 / 任务态 | 直接恢复 | 总结 §4.5 |
| 状态块当前值 + `schema_version` / `state_rev` | 恢复后写进新会话 | §2.2 |
| 最近若干轮对话记录（完整条目 schema） | 现有实践最近 12 轮【实测做法，轮数需按 §5.5 重新校准】 | 总结 §4.5 |
| 当前摘要对象及 `covers` | 避免重连后重新摘要 | §5.6 |
| 指代记忆（"刚说到的点"） | 写进状态块 | 总结 §4.5 |
| 工具调用登记：在途调用、已执行写操作的 `idempotency_key` 与结果 | 断线重放判定（§4.5）和本地收口（§4.6） | 本规范 |
| `session_seq`、人设 / 工具表版本 | trace 连续性 | 06 §3.2、§3.6 |
| B 类：表单与版本 | 恢复屏幕状态 | 架构 §3.2 |

- 存储：现有实践为 Redis（总结 §4.5），TTL = 会话恢复窗口。快照在每个回合终态后写一次（写时机与状态块检查点一致）。
- 不得把上游镜像写进快照。
- 快照不含原始音频。

### 8.3 多连接：前台租约与播报领取

同一用户会话可能同时出现多条连接（重连时旧连接未超时、同一账号多设备 / 多端）。规则：

1. **前台租约**（会话归属）：同一时刻只有一条连接持有用户会话的前台租约，只有持有者能驱动上游会话和出声。新连接领取时，旧连接的租约被收回，旧连接上的输出按代际丢弃。
2. **播报领取**（claim）：后端事件（到点提醒、后台任务完成）的播报用可续期的领取，防止多连接重复播或丢播，机制与参数以 02 §3.3 为准：TTL 60 s、每 TTL/3 续期一次；连接断开只释放领取，重连后可重新领取；送达以客户端 `playback.started` 回执为准，开始回执超时与重试上限按 02 §3.7、§3.6（A 类下发完成 + 5 s、最多 8 次；qwen 原值 120 s 对 A 类过长，不沿用）。【开源，参数为建议值，需实测】
3. 重连后不得重复播已送达的 narration（以回执为准），也不得重复执行在途写操作（§4.5）。

## 9. profile 差异

| 条目 | A：无界面硬件 | B：有界面移动端 |
|---|---|---|
| 用户会话边界 | 会话恢复窗口内连续；时长可很长 | 一任务一会话 |
| 主动换会话 | 定时回收 + 轮数阈值 + 状态粗变化，都是常规操作 | 任务内较少；主要由断线 / App 切后台 / 轮数触发 |

| 状态块形态 | 固定分节短文本，≤ 260 字【建议值，需实测】 | 表单：屏幕可见可改、有版本；进模型的是与当前阶段相关的字段子集 |
| 已播放文本 | 只有声音：按 `played_ms` 截取 | 声音 + 屏幕：上屏内容以文字化摘要计入 |
| 事件来源 | 多：设备事件、定时器、后台任务 → narration，是"自己的话"进历史的主要来源 | 少：模型 / 系统提示 / 转人工 |

| 历史投影 | 最近 K 轮 + 摘要 + 状态块 | 最近几轮 + 表单 + 摘要；级联回合即时拼装 |

| 重建期间反馈 | 必须有声音（本地 cue），2 s 内 | UI 状态 + 语音填充 |
| 多连接 | 设备单连接为主，重连时新旧连接交叠 | 多端 / 切后台，前台租约更常用 |

## 10. 验收要点与开放问题

### 10.1 验收要点

所有有竞态的指标用重复率（每组 ≥ 20 次，总结 §5.4 的 6 次太少，BP B.8），报告 P50 / P90。

| 指标 | 目标 | 实验 / 出处 |
|---|---|---|
| 早期信息召回（第 3 轮说名字，第 25、40 轮追问） | 摘要 / 截断方案不低于全量历史 | B-X4、E-B2 |
| 重建后首轮首音增量 | 【建议值，需实测】P90 ≤ +300 ms（相对同类回合非重建首轮） | B-X4 |
| 交接期音频丢失 | 0 | B-X4 |
| 写操作重复执行 | 0 | B-X3、E-B5 |
| 重连后重复工具调用 / 重发旧工具结果 | 0 | B-X3；PC-B §2.2 |
| 纯文本回复轮数（音频会话中 `reply_modality=text_only`） | 0 | B-X2、E-B4 |
| 首轮把历史当问题回答、模仿格式说话 | 0 | B-X2 |
| 回合终态率（断线注入：识别中 / 工具执行中 / 已回传未出声 / 出声中） | 100% | B-X3 |
| 多轮上下文用例 | ≥ 76/78；"开始吧"组 ≥ 15/16 | B-X5；总结 §5.4 基线 |
| 状态注入首音增量 | < 80 ms | B-X5、E-B3 |
| 无效重建次数（"重建也没用"类错误触发的重建） | 0；总量较现状下降 | B-X3、E-B6 |
| 用户需重说率（断线后） | 重放方案显著低于丢弃方案 | E-B5 |
| 状态块长度、人设硬规则、禁用词 | 自动检查通过 | §2.2、§2.3 |
| 进上游历史的 assistant 文本来源 | 100% 为 `text_presented`（抽查 trace） | §3.3 |

trace 必须覆盖 06 §3.6（会话与缓存）、§3.9（错误相关）的全部字段，以及 `prompt_version`（06 §3.2，含人设、工具表、状态块版本）。

### 10.2 开放问题
